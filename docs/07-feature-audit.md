Под таблицей — подробный разбор каждой строки с конкретными местами в коде и предложениями. Вердикты согласованы с планами в [03-feature-gap.md](docs/03-feature-gap.md) и [04-tech-stack-2026.md](docs/04-tech-stack-2026.md).

## Подробный разбор

### 1. Аутентификация — безопасность 1, DX 3, UX 3

Самая срочная проблема всего репозитория не архитектурная, а бытовая: в [auth.ts](packages/trpc/src/auth.ts#L13-L21) **клиентские секреты GitHub и Google захардкожены прямо в исходнике** и закоммичены в git. Даже для заброшенного прототипа это плохо: репозиторий достаточно сделать публичным один раз, и секреты скомпрометированы. Их нужно отозвать в консолях Google/GitHub и перевыпустить, а в коде читать из `process.env` — независимо от судьбы остального кода, это стоит сделать сегодня, секреты в истории git останутся навсегда. Остальное тоже прибито гвоздями: `baseURL: 'http://localhost:8484'`, `trustedOrigins: ['http://localhost:3000']`, callback `http://localhost:3000/studio` в [sign-in.tsx](packages/studio/src/routes/sign-in.tsx#L82) — продукт в принципе неконфигурируем для чужого окружения. Сессия на год (`expiresIn: 365 дней`) — слишком долго для админки, разумно 7–30 дней со скользящим продлением. В sign-in есть и логическая ошибка: `accs.data.length < 0` никогда не истинно (должно быть `=== 0`).

По UX вход через OAuth выглядит опрятно, и для центрального сервиса это уместная основа — но не единственная. **Предложение:** better-auth оставить; секреты и URL — только из env/конфига; добавить email/пароль для тех, кто не хочет связывать аккаунты; для студии на чужом домене — bearer-токены вместо кросс-доменных кук; и достроить второй контур доступа — API-ключи проекта (read/write) для клиентской библиотеки, которых сейчас нет вовсе (параметр `token` в `createJalykClient` принимается и никуда не передаётся).

### 2. Авторизация и роли — безопасность 1

В [t.ts](packages/trpc/src/routes/t.ts) tRPC инициализируется без контекста: ни одна процедура не знает, кто её вызывает, и ни одна не проверяет сессию. **Каждый эндпоинт — публичный.** Любой человек, знающий адрес сервера, может читать и перезаписывать поля любых документов любого проекта (`field.upsert` принимает `projectId` из инпута), выкачать список пользователей проекта (`project.find`), слушать поток изменений (`onFieldUpdate`). Роли `owner/editor/viewer` существуют только как enum в схеме БД. CORS с `origin: localhost:3000` — не защита: он не останавливает запросы не из браузера. **Предложение:** в новой версии — middleware аутентификации на все операции с первого дня (в Effect это один Layer), проверка прав в одной точке, а не в каждом обработчике; модель прав для MVP — «вошедший может всё», но точка проверки уже существует.

### 3. Мультитенантность — безопасность 1, DX 2

Сущность `Project` пронизывает всё (каждый запрос таскает `projectId`), но изоляция тенантов не обеспечивается нигде: `document.find` и `idsOfType` вообще не фильтруют по проекту — документы «чужих» проектов достаются по id или типу. Это классическая ловушка мультитенантности: один забытый where — и утечка. Для центральной модели мультитенантность — несущая конструкция, поэтому **предложение:** сохранить и реализовать по-настоящему. `projectId` выводится из аутентификации (сессия/ключ привязаны к проекту), а не передаётся клиентом в каждом инпуте; изоляция — в одной точке (middleware, подмешивающий фильтр по проекту во все запросы), покрытая самыми приоритетными тестами системы; как страховка — RLS в Postgres. План — в [04-tech-stack-2026.md](docs/04-tech-stack-2026.md).

### 4. user.upsert с клиента — безопасность 1

[user.ts](packages/trpc/src/routes/user.ts): клиент после OAuth-входа сам отправляет на сервер свой id, имя и фото, и сервер слепо делает upsert. Кто угодно может перезаписать имя и фото любого пользователя, зная его id, или насоздавать мусорных пользователей. Профиль должен создаваться сервером из данных auth-провайдера (better-auth это делает сам — здесь продублирована его работа, причём в отдельной таблице User параллельно таблицам better-auth). **Предложение:** отказаться; единственный источник пользователей — better-auth.

### 5. Хранение полей (EAV) — безопасность 3, DX 2, UX 4

Каждое поле — строка таблицы с ключом `(documentId, path)`. Подробный разбор уже сделан в [03-feature-gap.md](docs/03-feature-gap.md): чтение документа — сборка из десятков строк, фильтрация по значению почти не индексируется, осиротевшие пути при смене структуры, нет транзакционности документа. По безопасности нейтрально (3), с одной оговоркой: целостность данных — тоже свойство безопасности, а здесь документ может оказаться сохранённым наполовину. UX-выигрыш (точечная реактивность инпутов) — реальный и его стоит сохранить. **Предложение:** документ-как-JSON, diff на сервере при сохранении, события по изменённым путям — клиентская реактивность остаётся той же.

### 6. field.upsert — безопасность 1, DX 2, UX 4

Помимо отсутствия auth (см. п. 2), здесь три содержательные проблемы. Сервер принимает `value: z.json()` и пишет его без какой-либо проверки против схемы — вся валидация живёт в браузере, то есть её нет (любой клиент шлёт что угодно, включая мегабайтные объекты — лимита размера тоже нет). Документ создаётся неявно как побочный эффект первой записи поля, причём `documentType` приходит с клиента — можно создать документ несуществующего типа. И сам upsert написан через хак `value: { toJSON: () => value }` (обход типов Prisma) с авторским комментарием «slomano». UX-идея при этом правильная: автосохранение с дебаунсом и оптимистичным обновлением кеша в [field.ts студии](packages/studio/src/field.ts#L59-L103) ощущается отлично. **Предложение:** переделать — серверная валидация против схемы (схема должна быть доступна серверу, см. п. 18), явная операция создания документа, лимиты размера; автосейв-механику студии перенести как есть.

### 7. Live-обновления — безопасность 2, DX 4, UX 5

Лучшая часть проекта. Сервер эмитит `fieldUpdate/{projectId}`, студия держит одну подписку и точечно обновляет кеш TanStack Query по ключу пути — перерисовывается ровно один инпут. Это даёт UX уровня Sanity и выгодно отличает проект от Payload. Проблемы: подписка не проверяет права (поток изменений проекта может слушать кто угодно — утечка контента в реальном времени), `EventEmitter` в памяти процесса (ок для self-hosted, не ок для масштабирования — но масштабирование и не нужно), и подозрительная настройка `maxDurationMs: 5000` в [t.ts](packages/trpc/src/routes/t.ts#L9) — SSE-соединение принудительно закрывается через 5 секунд, то есть «вечная» подписка живёт на постоянных реконнектах. **Предложение:** сохранить архитектуру один-к-одному, транспорт — SSE из Effect Stream, фильтрация событий по правам подписчика.

### 8. Публичный API чтения — безопасность 1, DX 2

[api.ts](packages/trpc/src/routes/api.ts) — заглушка: принимает `query: z.custom()` (то есть любой объект без валидации) и возвращает **все поля всех документов проекта**, игнорируя query. Закомментированный «настоящий» вариант ещё опаснее: он разворачивает присланный клиентом объект прямо в `db.field.findFirst(...query)` — это инъекция запроса по построению: через `select`/`include` клиент достаёт смежные таблицы (пользователей, другие проекты), а `OmitRecursively` в типах его не останавливает, потому что типы не проверяются в рантайме. Токен `token` в `createJalykClient` принимается и никуда не передаётся. **Предложение:** сделать заново как типизированный `find` поверх известного серверу набора схем: сервер принимает только декларативный объект ограниченной формы (where по объявленным полям, select по объявленным ключам, дереференс по объявленным ссылкам), валидирует его против схемы и сам строит SQL. Никогда не принимать ORM-запросы с клиента.

### 9. Схема в коде — DX 3

`defineDocument`/`defineString`/`defineReference` — правильная идея и приятный API (иконки, варианты инпутов, zod-shape). Подводят три вещи: циркулярная типизация решена через `declare module` с авторской пометкой «wrong solution» (цели ссылок не выводятся, их надо дублировать руками); определения живут в пакете студии, поэтому сервер не знает схему (отсюда невозможность серверной валидации и типизированного find); `defineGroup` и массивы недоделаны — реально работают только string и reference. **Предложение:** сохранить идею, вынести определения в отдельный пакет, общий для сервера/студии/клиента, реестр `defineConfig({ documents: {...} })` для вывода типов (план в [03-feature-gap.md](docs/03-feature-gap.md)).

### 10. Встраивание студии — DX 2, UX 4

Компонент `Studio` тащит собственный `BrowserRouter` ([studio.tsx](packages/studio/src/studio.tsx)) внутрь приложения, где уже есть TanStack Router, — два роутера борются за один URL. Путь `/studio` захардкожен в [SegmentView](packages/studio/src/components/studio.tsx#L270) несмотря на существующий параметр `studioPath`. Стили: пользователь обязан импортировать CSS-файл, Tailwind-классы без префикса могут конфликтовать с хост-приложением. Хорошее: сама модель «студия = компонент на твоём маршруте» — это ключевая ценность продукта, и она работает. **Предложение:** переделать навигацию на memory-историю с синхронизацией через splat-маршрут хозяина, префикс для Tailwind, тема через CSS-переменные.

### 11. Структура студии — DX 2, UX 4

UX-концепция сегментов-колонок (Miller columns, как в Sanity) с подсветкой выбранного пути — хорошая, и рекурсивный `SegmentView` её уже реализует. Но вся структура — захардкоженный `testStructure` с тестовыми id (`shop_0`, `cool-user`), «создать документ» ведёт на id `'666'` вместо генерации cuid, поиск в списке — нерабочий input, у `DocumentForm` определение берётся как `definitions[1]!`. То есть фича — на стадии макета. Идея давать разработчику описывать структуру в конфиге (как `structureTool` в Sanity) правильная, но для MVP избыточная. **Предложение:** генерировать структуру из схемы автоматически (список типов → список документов → форма), кастомную структуру — после MVP.

### 12. Инпуты полей — DX 4, UX 2

DX разработчика схемы хороший: варианты `default/multiline/dropdown/select/editor` объявляются декларативно. Но из вариантов в [string-input.tsx](packages/studio/src/components/form/string-input.tsx) полноценно работает один: у default-инпута курсор прыгает в конец при ререндере (признано в todo-комментарии; классическая проблема controlled input + async-обновление кеша); textarea multiline вообще не привязана к значению (не показывает сохранённые данные); в dropdown `disabled={!!selected}` выключает **все** пункты после первого выбора — сменить значение невозможно, а выбор по `onMouseDown` ломает клавиатурную навигацию; вариант `select` объявлен в типах, но не реализован. Числового инпута нет в схеме (компонент есть, определения нет). **Предложение:** доделать на новой базе: локальный стейт инпута с синхронизацией от внешних обновлений только когда поле не в фокусе — это решает и курсор, и конфликт с live-обновлениями; Base UI Select вместо Menu для выбора значений.

### 13. Reference-поле — DX 3, UX 3

Концепт правильный и UI приличный (превью выбранного документа, поиск, очистка), но всё внутри захардкожено: документы ищутся только типа `'user'` (todo в коде), хотя схема объявляет `to: ['employee']`; поле поиска — декорация; превью — всегда `useUserPreview1`. Дереференс на чтении отсутствует — клиент получает `{_ref}` и дальше сам. **Предложение:** доделать: брать типы целей из определения, серверный поиск по превью-полям с лимитом, превью из схемы цели; дереференс — в `find` через вложенный select (п. 8).

### 14. Rich-text (Tiptap) — безопасность 2, DX 3, UX 2

Редактор существует, но не подключён к данным: контент захардкожен в `useEditor`, `upsertField` не вызывается, `placeholder` не используется. Тулбар — только три заголовка, при этом `shouldRerenderOnTransaction: true` перерисовывает весь редактор на каждое нажатие. Расширение `reference` (ссылки на документы внутри текста) — задел на сильную фичу, у конкурентов такие inline-ссылки любят. Безопасность 2 — на вырост: rich-text, который где-то отрендерится как HTML, требует санитизации на выходе; об этом стоит подумать в момент, когда появится сериализация. **Предложение:** доделать: хранить Tiptap JSON через тот же upsert-механизм с дебаунсом, тулбар — bold/italic/списки/ссылки/заголовки, перерисовка через `useEditorState` точечно.

### 15. Превью документов — DX 4, UX 4

Паттерн «хук-стратегия `usePreview`, возвращающий `{title, subtitle, media}`» — удачный: превью может тянуть данные асинхронно и подписываться на обновления, а компонент один. Минус: превью задаётся в месте использования, а не в определении документа, поэтому одному типу легко назначить разные превью случайно, и автоматического фолбэка «первое строковое поле → title» (задуман в README) нет. **Предложение:** сохранить; превью по умолчанию объявляется в `defineDocument` (как `preview` в Sanity), хук-стратегия остаётся как переопределение.

### 16. Ассеты — безопасность 1, DX 2, UX 3

Самая забагованная фича. Главное: **удаление не работает по построению** — [buildAssetKey](packages/trpc/src/s3/index.ts#L17-L28) добавляет к имени случайный ulid-префикс при каждом вызове, поэтому `deleteAsset` строит новый ключ, которого в бакете нет, и молча «удаляет» несуществующий объект. Дальше по списку: файл передаётся строкой через JSON-body tRPC (бинарные данные через base64 в JSON — лишние 33% объёма и память на буферизацию; правильный путь — multipart или presigned upload), лимита размера нет, тип файла не проверяется (можно залить html/js — а это вектор stored XSS, если бакет раздаётся с того же домена), креды S3 читаются как `process.env.S3_ID!` без проверки наличия, endpoint Яндекса захардкожен, метаданных в БД нет (картинку нельзя связать с полем документа — поле image в схеме вообще отсутствует), `path.join` для S3-ключей даст `\` на Windows-сервере. UI списка с категориями по типам — неплохой каркас, но без загрузчика с прогрессом и без выбора ассета в поле документа фича не замкнута. **Предложение:** переделать по плану MVP: S3 остаётся (для центральной модели это правильный выбор), но появляется таблица assets в БД с привязкой к проекту (ключ хранится, а не вычисляется — это чинит удаление), presigned-загрузка напрямую в хранилище с лимитами и whitelist типов (объём — будущая ось квот), поле `image` в схеме, отдача через CDN.

### 17. HTTP-сервер — безопасность 2, DX 3

[apps/server](apps/server/src/index.ts) — 25 строк: CORS на localhost, tRPC-адаптер, better-auth handler. Порт, origin и всё остальное захардкожено; `bodyParser.json()` подключён **после** роутов, то есть не делает ничего (к счастью — tRPC парсит body сам); rate limiting и лимитов размера тела нет, CORS один на всех вместо разрешённых origin'ов по проектам. По роли этот пакет — зародыш будущего центрального API-сервера, но содержимого в нём нет. **Предложение:** переписать как полноценное отдельное приложение `apps/api` на Effect HttpApi: конфиг из env, CORS по списку origin'ов проекта, rate limiting, лимиты тела, healthcheck, учёт запросов; деплой отдельно от сайта-платформы, чтобы падение одного не задевало другое (план — в [04-tech-stack-2026.md](docs/04-tech-stack-2026.md)).

### 18. Валидация значений — безопасность 1, DX 3, UX 3

Zod-shape у поля используется в трёх местах студии: парсинг прочитанного значения (показ ошибок несоответствия — хорошая идея, прямо отвечающая сценарию «тип поля изменили, старые данные не подходят»), проверка перед upsert (но при ошибке — только `console.warn`, пользователь ничего не видит), и... всё — сервер не валидирует ничего (см. п. 6). Правил `required/min/max` нет, сообщений об ошибках в UI нет. В [field.ts студии](packages/studio/src/field.ts#L30) рядом живёт показательный хак — импорт типов из `node_modules/.../getQueryKey.d-CruH3ncI.mjs` по захардкоженному имени бандла, который сломается при любом обновлении tRPC. **Предложение:** переделать по плану: декларативные правила в определении поля (сериализуемы — значит, доступны и серверу, и UI), валидация на сервере обязательна, на клиенте — для мгновенной обратной связи с показом ошибки у поля.

## Общие выводы

Паттерн, который повторяется в большинстве строк: **UX-идеи и клиентская механика — сильные** (реактивные поля, автосейв с дебаунсом, превью-стратегии, колонки структуры — оценки 4–5), а **серверная половина почти отсутствует как продукт** (безопасность 1–2 везде: нет аутентификации запросов, нет серверной валидации, нет изоляции данных). Это нормальная форма прототипа, который писался от интерфейса, но это же объясняет, почему проект застрял: следующий шаг требовал серверной архитектуры, а она была временной по замыслу.

Отсюда два практических следствия. Первое: переписывание по [04-tech-stack-2026.md](docs/04-tech-stack-2026.md) — это не «выбросить всё»: клиентский слой студии (пп. 7, 12–15) переносится с заменой транспорта, а заново пишется именно серверная половина, которая и так не дожила бы до продакшена. Второе: три вещи стоит сделать немедленно, ещё до любого переписывания — отозвать и перевыпустить OAuth-секреты из п. 1, убрать их в env, и не разворачивать текущий сервер ни на какой публичный адрес даже «на посмотреть».

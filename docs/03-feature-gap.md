# Разрыв по функционалу: что переделать и что добавить

Этот документ отвечает на два вопроса. Первый — какие из уже существующих в Jalyk механизмов нужно переделать, потому что в текущем виде они не доживут до взрослого продукта. Второй — каких фич нет вовсе, хотя они есть у конкурентов: у Payload и Sanity (прямые конкуренты по нише headless CMS для разработчиков), и у Битрикса с 1С (конкуренты по аудитории бизнеса; что именно у них есть и почему это работает — разобрано в [02-bitrix-1c-comparison.md](docs/02-bitrix-1c-comparison.md)).

Сразу оговорка о приоритетах. Не всё перечисленное ниже нужно делать — и тем более не всё нужно делать сразу. Часть фич относится к MVP ([05-mvp.md](docs/05-mvp.md)), часть — к долгосрочному плану ([06-long-term.md](docs/06-long-term.md)), а часть честно помечена как «не стоит делать вообще». Здесь они собраны вместе, чтобы была полная карта.

## Часть 1. Что нужно переделать в существующем

### Хранение контента: от EAV-полей к документу как JSON

Самое фундаментальное решение, которое стоит пересмотреть, — хранение каждого поля отдельной строкой таблицы `Field` с ключом `(documentId, path)`. Оно было выбрано ради точечной реактивности (обновляется одно поле — перерисовывается один инпут), но цена слишком высока:

- Чтение документа целиком — это сборка из десятков строк с восстановлением вложенности из путей вида `animals.cats.0`. Любой запрос с фильтром по значению поля превращается в поиск по парам путь/значение, что не индексируется нормальным способом.
- Перестройка структуры (массив стал объектом) оставляет в базе осиротевшие пути — в README этот сценарий описан, и он не решается красиво в принципе.
- Транзакционность документа исчезает: документ может оказаться наполовину сохранённым.
- Язык запросов для клиента сайта (главная нерешённая задача проекта, `api.field` так и остался заглушкой) поверх такой схемы спроектировать намного тяжелее, чем поверх обычного JSON.

Все конкуренты хранят документ единым JSON-объектом (Sanity — документы в Content Lake, Payload — строка в таблице коллекции, Directus — строка в обычной таблице). Точечная реактивность при этом достижима и без EAV: сервер при сохранении вычисляет diff между старой и новой версией документа и шлёт в событие только изменённые пути — клиентская часть с подпиской инпутов на пути остаётся ровно той же, меняется лишь то, кто вычисляет «что изменилось». Это та часть текущей архитектуры, которую стоит сохранить: схема подписок «один WebSocket/SSE на студию, инвалидация по ключу пути» — хорошая идея.

Рекомендуемая модель: таблица `documents` со столбцами `id`, `project_id`, `type`, `data` (JSONB), `created_at`, `updated_at`, плюс служебные столбцы по мере появления фич (`status` для черновиков, `locale` для локализации). Postgres с JSONB и GIN-индексами закрывает фильтрацию по полям документа быстро и без танцев, а составной индекс по `(project_id, type)` — основной паттерн выборок.

### Язык запросов и публичный клиент

Сейчас `createJalykClient` отдаёт метод `field(query)`, где query — это Prisma-подобный тип `FindFirstFieldSafe`, который сервер игнорирует. Наброски в README (select по типам документов, where с фильтрами, дереференс ссылок с указанием подзапросов на каждый возможный тип) — это, по сути, изобретение GROQ заново, и сам автор пометил один из вариантов как «звучит как хрень».

Что нужно вместо этого. Поскольку определения документов уже описаны в коде и доступны клиенту (они передаются в `createJalykClient`), правильный путь — типизированный query builder, выводящий типы из определений: `client.find('shop', { where: ..., select: { title: true, director: { select: { name: true } } } })`. Дереференс ссылки — это просто вложенный select: тип поля `director` известен из определения (`to: ['employee']`), значит и форма вложенного select выводится статически. Это решает и проблему «селект на юнион типов» из README: если ссылка может указывать на несколько типов, select становится объектом с ключом по каждому типу — но это выводится из схемы, а не пишется руками.

Важно не делать: собственный текстовый язык запросов (как GROQ). Это огромная работа (парсер, планировщик, документация), которую Sanity могла себе позволить, а одиночный проект — нет. Центральная модель этого и не требует: typed builder сериализуется в JSON-дерево ограниченной формы, оно передаётся по сети, а сервер валидирует его против схемы проекта и сам строит SQL. Тот же результат, что у строкового языка, но без парсера и с типобезопасностью на клиенте.

### Типизация определений документов

Циркулярная зависимость типов (документ `shop` ссылается на `employee`, и оба должны знать друг о друге) сейчас «решена» через `declare module` с пометкой wrong solution. Стандартное решение этой задачи — паттерн реестра, как в Payload и Drizzle: все определения собираются в один объект `defineConfig({ documents: { shop, employee } })`, и типы ссылок выводятся из ключей этого объекта, а не из глобального интерфейса. Ссылочное поле объявляет цель строкой (`to: ['employee']`), а проверку того, что такая строка — ключ реестра, делает дженерик на уровне `defineConfig`. Так работают и `relations()` в Drizzle, и `CollectionConfig.slug` в Payload — задача решённая, нужно лишь аккуратно перенести паттерн.

### Аутентификация и доступ приложений

Для центрального сервиса OAuth через Google/GitHub — уместный выбор (вход в один клик, не нужно хранить пароли), его стоит дополнить email/паролем для тех, кто не хочет связывать аккаунты; better-auth умеет и то и другое, его можно оставить. Что нужно переделать: секреты провайдеров сейчас захардкожены в коде (см. [07-feature-audit.md](docs/07-feature-audit.md)) — только env и конфиг. Чего не хватает целиком — **второго контура доступа, API-ключей**: человек входит в студию своим аккаунтом, но приложения (сайт, читающий контент через `@jalyk/client`) аутентифицируются ключом проекта с правами read или read/write, как у Sanity. Ключи создаются и отзываются на сайте управления, проверяются API-сервером на каждый запрос, и через них же считается статистика использования по проектам.

### Ассеты

S3-совместимое хранилище — правильный выбор для центральной модели, но реализацию нужно переделать: сейчас метаданные ассетов не хранятся в БД (всё выводится из листинга бакета), удаление не работает из-за бага с генерацией ключа, загрузка идёт base64-строкой через JSON (см. [07-feature-audit.md](docs/07-feature-audit.md)). Нужны: таблица ассетов с привязкой к проекту, presigned-загрузка напрямую в хранилище, лимиты и whitelist типов (квоты по хранилищу — будущая основа тарифов), минимальная обработка изображений (ресайзы через sharp), отдача через CDN.

## Часть 2. Чего нет, но есть у Payload и Sanity

Ниже — инвентаризация по убыванию важности. Метки: **[MVP]** — без этого продукт не воспринимается как CMS; **[v1]** — нужно взрослому продукту; **[потом/нет]** — осознанно отложить или не делать.

### Черновики, публикация и версии [MVP — в минимальном виде]

И Payload (versions + drafts), и Sanity (draft-документы, Releases) позволяют редактировать контент, не ломая опубликованный сайт, и откатываться к прошлым версиям. В Jalyk любое изменение поля немедленно становится «правдой» для сайта — для реального заказчика это неприемлемо: редактор не может подготовить материал заранее. Минимум для MVP: статус draft/published у документа и кнопка «Опубликовать» (публикация копирует draft-данные в published-данные). История версий (таблица `document_versions`, просмотр и откат) — v1.

### Контроль доступа [v1]

В Payload access control — это функции на уровне коллекции, операции и поля (`access: { read: ({ req }) => ... }`), у Sanity и Directus — роли с гранулярностью до поля. В Jalyk роли есть только как enum в схеме БД, ни одна проверка не написана. Для MVP достаточно «все аутентифицированные могут всё», но архитектурно стоит сразу заложить место, где проверка прав вызывается (один middleware на все операции с документами), чтобы потом не разносить проверки по пятидесяти местам.

### Хуки и серверная логика [v1]

`beforeChange`/`afterChange`/`beforeValidate` в Payload — это то, что превращает CMS в платформу для приложений: слаги, вычисляемые поля, отправка писем, синхронизация с внешними системами. Это же — аналог встроенного языка 1С (бизнес-логика живёт в конфигурации). В Jalyk определения чисто декларативные. Добавить хуки в `defineDocument` относительно дёшево, а ценность большая — рекомендую в раннюю v1.

### Live preview [v1]

Payload даёт live preview (сайт в iframe рядом с формой, обновляется при наборе), Sanity — целое визуальное редактирование с оверлеями (клик по тексту на сайте открывает нужное поле). Это одна из самых продающих фич современных CMS. У Jalyk, по иронии, уже есть половина механизма — реактивные подписки на пути; осталось дать фронтенду пользователя клиентский хук, который подписывается на те же события и обновляет данные на странице. Полное визуальное редактирование с оверлеями — [потом].

### Локализация [v1]

У Payload локализация на уровне поля (`localized: true`), у Sanity — паттерны на уровне документа или поля. Для российского рынка (RU/EN как минимум) отсутствие i18n отсекает заметную часть заказчиков. Разумная модель при document-as-JSON: локализуемые поля хранят объект `{ ru: ..., en: ... }`, схема знает, какие поля локализованы, студия показывает переключатель языка.

### Медиабиблиотека [MVP — базовая]

У всех конкурентов: централизованная библиотека, метаданные (alt, подписи), варианты размеров изображений, фокус-поинт у Sanity. MVP: загрузка на диск, список с превью, выбор в reference-поле, ресайзы. Фокус-поинты, видео, обработка на лету — [потом].

### Валидация и обязательность полей [MVP]

Сейчас валидация — только zod-shape для соответствия типу. Нет required, min/max, уникальности, кастомных правил с сообщениями. Это дешёво добавить в определения полей и без этого нельзя называться CMS.

### Webhooks [v1]

Стандарт индустрии: при изменении контента дёрнуть URL (пересборка статического сайта, инвалидация кеша, уведомление). Делается за день-два, нужен для любого продакшен-сценария со статической генерацией.

### Поиск по контенту [v1]

Полнотекстовый поиск в студии (и опционально в API). С Postgres это почти бесплатно: встроенный full-text search (`tsvector` + GIN) покрывает потребности студии без отдельного поискового движка.

### Совместное редактирование в реальном времени [потом]

Фирменная фича Sanity — одновременное редактирование документа как в Google Docs, с присутствием (кто сейчас в документе — в README Jalyk есть такая идея, «как истории в тг»). Честная реализация требует CRDT или OT — это месяцы работы. Текущая модель Jalyk (последняя запись побеждает + live-обновления у всех) — разумный компромисс надолго. Индикатор присутствия без совместного курсора — дёшево и можно в v1.

### Scheduled publishing, A/B, workflow согласования [потом/нет]

Публикация по расписанию — несложно (поле `publish_at` + проверка при чтении), можно в v1. Workflow с согласованием (draft → review → approved) и A/B-тесты — корпоративные фичи, в обозримом плане не нужны.

### REST/GraphQL API [нет — осознанно]

Payload и Directus автоматически дают REST и GraphQL. Для Jalyk с его типизированным клиентом GraphQL — лишний слой; типизированный RPC-клиент покрывает основной сценарий лучше. Простой REST для чтения (для не-JS потребителей) — дёшево и можно в v1, GraphQL — не делать.

### AI-функции [потом, но держать в уме]

К 2026 году у конкурентов это уже не экзотика: Payload встроил auto-embedding для RAG и официально меряет, насколько хорошо AI-агенты пишут код под его API; у Sanity — AI Assist для генерации и перевода контента. Для маленького проекта реалистичный вход — не свои модели, а удобство для чужих агентов: хорошая документация схемы, MCP-сервер или просто чистый typed API, чтобы Claude/Cursor могли наполнять и читать контент. Это дёшево и неожиданно сильно продаёт продукт разработчикам.

## Часть 3. Чего нет, но есть у Битрикса и 1С — и что с этим делать

Подробный разбор в [02-bitrix-1c-comparison.md](docs/02-bitrix-1c-comparison.md); здесь — выжимка в терминах фич.

**Готовые вертикальные решения (магазин, корпсайт, блог).** У Битрикса это главный продукт, у 1С — типовые конфигурации. Аналог для Jalyk — стартовые наборы определений + готовые фронтенд-шаблоны: `create-jalyk-app --template blog`. Это не фича ядра, а контент вокруг него, и по соотношению усилия/эффект для привлечения пользователей это едва ли не лучшее вложение после MVP.

**Интеграции с учётом, платежами, доставкой.** Для Jalyk прямые интеграции с 1С/СДЭК/ЮKassa — нереалистичный объём. Правильный ответ — webhooks и хуки, через которые такие интеграции пишет разработчик внедрения. Конкурировать за заказчика, которому нужен обмен с 1С из коробки, не нужно — это не наша аудитория.

**Маркетплейс модулей.** Сетевой эффект, который не построить волевым решением. Предусловие — система плагинов в ядре ([06-long-term.md](docs/06-long-term.md)), сам маркетплейс — далёкая перспектива.

**Обновления, не ломающие доработки (механизм 1С).** В мире кода это решается иначе и проще: semver самого пакета + механика миграций контента при изменении схемы (изменил тип поля в определении — получи скрипт миграции данных, как `prisma migrate`, но для контента). Вот это стоит сделать фичей: ни у Payload, ни у Sanity нет хорошего ответа на «я поменял схему, что теперь с существующим контентом», и у Jalyk эта боль уже отрефлексирована в README (валидация формы против устаревших данных). Это потенциальная, но вполне реальная точка дифференциации.

**Визуальный конструктор страниц.** У Битрикса есть, у headless CMS — нет (кроме блочных редакторов вроде blocks-поля в Payload). Для Jalyk достаточно поля типа «массив блоков» (повторяемые группы с выбором типа блока) — это покрывает 80% сценария «редактор собирает лендинг» и не требует визуального конструктора.

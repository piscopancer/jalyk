# Jalyk: что это за проект и как он реализован

## Замысел

Jalyk — это headless CMS по образцу Sanity. Идея в том, что разработчик описывает структуру контента в коде (документы и их поля), встраивает готовую админку («студию») в своё React-приложение на отдельном маршруте, а редакторы через эту студию наполняют контент. Сайт пользователя затем читает этот контент через типизированный клиент.

Важная особенность текущей реализации: **сервер и база данных — центральные и принадлежат автору проекта**. У пользователя на его хостинге живёт только React-приложение со встроенной студией, а все запросы (и из студии, и из клиента сайта) уходят на центральный сервер `localhost:8484` (в проде это был бы сервер автора) с общей базой Postgres. Мультитенантность сделана через сущность `Project`: каждый документ привязан к проекту, у проектов есть пользователи с ролями. Это модель Sanity (их Content Lake), а не модель Payload/Strapi, где пользователь хостит всё сам. В июне 2026 принято решение развивать именно эту модель: центральная инфраструктура с сайтом управления проектами, API-ключами, сбором статистики и в перспективе подписками; разработчикам поставляются только npm-пакеты студии и клиента.

## Структура монорепо

Монорепо на pnpm workspaces + Turborepo. Две группы пакетов:

- `apps/server` — тонкая обёртка: Express-сервер на порту 8484, который подключает CORS (фронт на `localhost:3000`), tRPC-адаптер из `@repo/trpc` и обработчик better-auth (`/api/auth/*`).
- `apps/test-client` — тестовое приложение пользователя: Vite + React 19 + TanStack Router + Tailwind 4. На маршруте `studio/$` монтируется компонент `Studio` из `@repo/studio`, а в `studio.ts` объявлена конфигурация с определениями документов (`shop`, `user`). В `cms.ts` создаётся клиент `createJalykClient` для чтения данных с сайта.
- `packages/trpc` — фактически весь бэкенд: схема Prisma (Postgres), tRPC-роутеры (`project`, `document`, `field`, `asset`, `user`, `api`), better-auth с провайдерами Google/GitHub, загрузка файлов в S3, WebSocket-сабскрипшены. Экспортируется как пакет и подключается в `apps/server`.
- `packages/studio` — встраиваемая админка: React-компонент `Studio`, внутри собственный роутинг на react-router (вход, структура, документы, ассеты), формы полей (строка, число, ссылка, ассет), редактор Tiptap 3, состояние через TanStack Query + tRPC, стили на Tailwind 4 и Base UI (beta). Собирается tsup, экспортирует JS и CSS-файл, который пользователь подключает у себя.
- `packages/client` — публичный клиент `@jalyk/client`: функция `createJalykClient({ projectId, token, definitions })`, которая ходит в эндпоинт `api.field` по tRPC.
- `packages/ui` — общие UI-компоненты (button, tooltip, menu, separator) на Base UI.

## Модель данных

Схема Prisma ([schema.prisma](packages/trpc/schema.prisma)) минимальная: `User` (создаётся auth-провайдером), `Project`, `UserProjectRole` (роли owner/editor/viewer), `Document` и `Field`.

Ключевое решение — **хранение контента по принципу EAV**: документ не хранит свои данные одним JSON-объектом, а разбит на отдельные строки таблицы `Field` с составным ключом `(documentId, path)` и значением `value Json?`. Путь — строка вида `animals.cats.0`, то есть вложенные объекты и массивы «расплющены» в плоские записи. У документа в базе есть только `id`, `type` и `projectId` — вся типизация и валидация живёт на клиенте, в определениях схемы.

Смысл этого решения — точечная реактивность: каждый инпут в студии подписан на свой путь, и при изменении одного поля сервер через `EventEmitter` + tRPC-subscription шлёт событие `fieldUpdate/{projectId}`, а перерисовывается только один инпут из сотни (логика описана в [README.md](README.md)). Это красиво для live-редактирования, но создаёт большие сложности для запросов: чтобы прочитать документ целиком, его нужно собирать из множества строк; чтобы сделать выборку «магазины, где location = russia», нужно искать по парам путь/значение; дереференс ссылок (`_ref`) требует рекурсивного обхода.

## Схема контента в коде

Студия настраивается через объект `StudioConfig { projectId, definitions }`. Определения строятся фабриками `defineDocument`, `defineString`, `defineReference`, `defineGroup` ([structure/index.ts](packages/studio/src/structure/index.ts)). У строкового поля есть варианты инпута: обычный, многострочный, dropdown/select с предопределёнными значениями, rich-text редактор (Tiptap). У поля можно задать иконку (lucide) и заголовок. Валидация значений — zod-схемы (`shape`), прикреплённые к определению поля. Подход скопирован с Sanity (`defineType`/`defineField`) и идейно близок к 1С: платформа одна, а разработчик пишет конфигурацию под конкретного заказчика.

## Что реализовано, а что нет

Работает в той или иной степени: вход через Google/GitHub, структура студии с превью документов, формы с инпутами и upsert полей по пути с дебаунсом, live-обновления по подписке, загрузка ассетов в S3, Tiptap-редактор со ссылками на документы.

Не доделано или сломано (по коду и [todo.md](todo.md)):

- Публичный API для сайта (`api.field` в [api.ts](packages/trpc/src/routes/api.ts)) фактически заглушка: принимает нетипизированный `query` и возвращает все поля проекта; настоящая фильтрация закомментирована. Язык запросов (аналог GROQ или Prisma-подобный select с дереференсом ссылок) так и не спроектирован до конца — в README остались наброски.
- `field.upsert` помечен как «сломано»: upsert документа с вложенным upsert поля написан с обходным трюком `toJSON`.
- Циркулярные зависимости типов в определениях документов (последние коммиты как раз об этом): ссылочное поле должно знать типы других документов, и это решено через костыль `declare module ... CustomDocumentDefinitions` с пометкой «wrong solution».
- Нет ролей в действии (роли есть в схеме, но проверки прав в роутерах отсутствуют), нет черновиков/публикации, нет истории версий, нет локализации, нет поиска, нет webhooks.
- Типобезопасность местами выключена (`z.custom()`, `as`-касты, `null!`).

## Что отделяет прототип от целевой модели

Целевая модель подтверждает направление, в котором прототип и был построен: централизованный сервис в духе Sanity. Но между прототипом и этой моделью лежат три больших разрыва. Первый — безопасность: код написан так, будто сервис доверенный, хотя центральная модель означает хранение чужого контента, и здесь нет ни проверки сессий в процедурах, ни изоляции проектов, ни API-ключей (подробный аудит — [07-feature-audit.md](docs/07-feature-audit.md)). Второй — отсутствует управляющий контур: негде создать аккаунт и проект, пригласить людей, раздать роли, выпустить ключ доступа — сейчас проект `la` и его пользователи появляются в базе руками. Третий — публичный API чтения, ради которого клиенты и подключаются, так и остался заглушкой. План переписывания под целевую модель описан в [04-tech-stack-2026.md](docs/04-tech-stack-2026.md) и [05-mvp.md](docs/05-mvp.md).

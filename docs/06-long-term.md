# Долгоживущий проект: куда расти после MVP

Этот документ описывает взрослый продукт, который получается из MVP ([05-mvp.md](docs/05-mvp.md)) последовательными улучшениями, без переписываний. Горизонт — два-три года. Модель — центральная платформа (как у Sanity): инфраструктуру держит автор, разработчики получают студию и клиент, деньги приходят с подписок и квот. Структура: продуктовая рамка, монетизация (теперь это часть архитектуры, а не примечание), этапы развития, сквозные практики, риски.

## Продуктовая рамка

**Для кого.** Основная аудитория — React-разработчики и маленькие студии, делающие кастомные сайты заказчикам: портфолио, корпоративные сайты, блоги, каталоги. Им нужна админка для заказчика, типизированный контент для себя и нулевая возня с инфраструктурой — создал проект на сайте и поехал. Для русскоязычного рынка есть дополнительный аргумент: данные в России (152-ФЗ), оплата в рублях без зарубежных карт — то, чего Sanity и Contentful дать не могут.

**Позиционирование.** «Sanity по-человечески»: та же модель (центральное хранилище, встраиваемая студия, типизированный клиент), но проще на порядок — без GROQ (типизированный builder вместо языка запросов), с щедрым бесплатным тарифом, с реактивной студией из коробки и с поддержкой на русском. Не конкурируем: с Payload за self-hosted аудиторию (осознанно — мы выбрали обратную модель), с Битриксом за «магазин под ключ», с энтерпрайзом Sanity/Contentful за корпорации.

**За счёт чего живёт.** Классическая воронка SaaS для разработчиков: бесплатный тариф достаточно щедрый, чтобы на нём жили пет-проекты и маленькие сайты (они — маркетинг), платный — для проектов заказчиков, где разработчик перекладывает стоимость на клиента. Ориентир цен — Sanity ($15/место/месяц) и местный рынок; реалистично 500–1000 ₽/проект или место в месяц. Квоты как оси тарифов: число участников проекта, число документов, запросы API в месяц, объём хранилища и трафика — всё это уже считается счётчиками из MVP.

## Этап 1 → v0.x: надёжная основа (3–4 месяца после MVP, весна 2027)

Цель — чтобы первые чужие продакшен-проекты жили на платформе и не разочаровались, а инфраструктура выдерживала рост без ручного труда.

- **История версий и откат.** Таблица `document_versions`, запись при публикации, просмотр и восстановление в студии. 2–3 недели.
- **Хуки.** `beforeValidate`, `beforeChange`, `afterChange`, `afterPublish`. Тонкость центральной модели: код хуков живёт в приложении разработчика (студия выполняет их при редактировании), серверная часть — только декларативная (вычисляемые слаги, простые правила); произвольный чужой код на нашем сервере не выполняем — это осознанная граница. 2 недели.
- **Webhooks.** Настройка на сайте-платформы, отправка с ретраями, лог доставки. Закрывает пересборку статических сайтов и интеграции. 1–1.5 недели.
- **Изображения.** Ресайзы при загрузке, варианты в find и студии, alt-тексты, отдача через CDN. 2 недели.
- **Поиск.** Postgres FTS по текстовым полям, поиск в студии. 1 неделя.
- **Write-API для клиента.** Ключи с правом write начинают что-то значить: создание и изменение документов из кода (импорт контента, скрипты наполнения). 1–2 недели.
- **Бэкап/экспорт проекта пользователем.** Кнопка «выгрузить весь проект» (JSON + ассеты). Для центральной модели это вопрос доверия: люди должны видеть, что их контент не заперт. 1 неделя.
- **Эксплуатация.** Алерты, дашборд нагрузки, rate limiting по ключам и IP, постановка восстановления из бэкапа на регулярную проверку. Фоном весь этап.

## Этап 2 → v1.0 + запуск оплаты (4–6 месяцев, осень 2027 — зима 2027/28)

Цель — продукт, за который не стыдно брать деньги, и включение биллинга.

- **Биллинг.** Тарифы (free/pro, возможно agency), оплата ЮKassa (рубли) и опционально Paddle/Stripe (валюта), страница подписки в кабинете, мягкое поведение при превышении квот (предупреждение → троттлинг, не выключение). Это большой кусок: 4–6 недель с учётом краёв (смена тарифа, неоплата, возвраты).
- **Миграции контента при изменении схемы** — флагманская продуктовая фича версии (идея из механизма обновлений 1С, разбор — [08-1c-platform-explained.md](docs/08-1c-platform-explained.md)). Сервер хранит версии снапшота схемы; при синхронизации новой версии — diff с классификацией (безопасно/требует решения), затронутые документы, миграции как код в конфиге разработчика с реестром выполненного в базе. Ни у Sanity, ни у Payload нет хорошего ответа — точка дифференциации. 4–6 недель.
- **Локализация.** `localized: true` у поля, хранение `{ ru, en }`, переключатель в студии, locale в find с fallback. 3–4 недели.
- **Live preview.** Хук в `@jalyk/client/react`: фронтенд разработчика подписывается на тот же SSE-поток и обновляет страницу при наборе в студии; режим «студия + iframe». Реактивная архитектура делает это дешевле, чем у конкурентов. 2–3 недели.
- **Блочное поле** (`blocks` — массив групп с выбором типа и drag-and-drop) — сценарий «редактор собирает лендинг из секций». 2–3 недели.
- **Присутствие.** Кто в документе (аватарки), предупреждение при одновременном редактировании поля. Без CRDT. 1–2 недели.
- **Кастомные роли и полевые права.** 2–3 недели.
- **Документация как продукт:** сайт документации (на TanStack Start, делит UI с платформой), рецепты, quickstart-шаблоны `create-jalyk-app` (blog/portfolio/catalog). К 1.0 — обязательный рывок.

## Этап 3 → платформа и экосистема (2028+)

Сюда входить, только если этапы 1–2 нашли пользователей и появились первые деньги.

- **Плагины студии** (типы полей, страницы, тулбары) как npm-пакеты; серверные расширения — осторожно и декларативно (граница «чужой код у нас не выполняется» остаётся).
- **Каталог шаблонов и плагинов** на сайте — зародыш маркетплейса по модели 1С: разработчики продают готовые конфигурации («магазин», «ресторан», «портфолио студии») с фронтендом.
- **AI.** MCP-сервер поверх typed API (агент заказчика наполняет и читает контент), AI-перевод локализаций, генерация alt-текстов. К 2028 — ожидаемый минимум для CMS.
- **Организации-команды** (агентство управляет проектами клиентов из одного кабинета) — путь к agency-тарифу.
- **Геораспределение/масштабирование** (read-реплики, регионы) — по фактической нагрузке, не раньше.
- **Co-editing на CRDT** — только при явном спросе; присутствие + live-обновления, вероятнее всего, закрывают потребность навсегда.

## Сквозные практики

С первого дня: тесты изоляции проектов и контрактные тесты API (это сервис с чужими данными — регрессии недопустимы), changesets и semver для пакетов, CI, staging-окружение перед продом, миграции БД только вперёд-совместимые (web и api деплоятся раздельно). С MVP: статус-страница и канал объявлений о работах — для платного сервиса это гигиена; политика данных и оферта — к моменту включения оплаты; имя проверить на благозвучность до публикации пакетов. Витрина (лендинг с демо-видео) — к MVP: продукт без витрины не существует.

## Риски и трезвый взгляд

Главный риск центральной модели — **обязательства**: с первым чужим продакшен-проектом появляется дежурство. Упавший API в субботу — твоя суббота; утечка данных — твоя репутация и юридическая ответственность; хранение персональных данных россиян — 152-ФЗ с реестровыми формальностями. Это цена, которую self-hosted модель не просила, и её надо принимать осознанно: managed-сервисы (БД, мониторинг) и консервативный деплой сводят дежурство к редким событиям, но не к нулю.

Второй риск — экономика: инфраструктура стоит денег с первого дня (VPS + managed Postgres + S3 + почта — порядка 3–7 тысяч ₽/месяц на старте), а доходы — с этапа 2. Это терпимо как цена хобби-проекта, но закладывает мотивацию не затягивать с биллингом. Третий — рынок: Sanity и Contentful сильнее во всём, кроме простоты, цены и локальности — поэтому держаться ниши (русскоязычные разработчики и студии, маленькие проекты) и дифференциаторов: реактивная студия, типизация от конфига до запроса без GROQ, миграции контента, данные и оплата в России. Четвёртый — одиночная разработка: оценки даны с запасом, скоуп каждого этапа режется вдвое без потери смысла этапа.

Если просуммировать: MVP к началу 2027, надёжная v0.x к весне 2027, v1.0 с биллингом, миграциями и локализацией к зиме 2027/28, экосистема — с 2028 года.

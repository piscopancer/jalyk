# MVP

## Что доказывает MVP

MVP должен доказать одну фразу: **«React-разработчик регистрируется, создаёт проект, получает ключ, встраивает студию в своё приложение и через полчаса читает типизированный контент с нашего API»**. Всё, что не работает на эту фразу, из MVP выбрасывается. Денег MVP не просит — бесплатный сервис на этом этапе, но статистика использования собирается с первого дня: она дешёвая, а без неё не спроектировать будущие тарифы.

Критерий готовности — сценарий от начала до конца, который можно показать в двух-трёхминутном видео:

1. Разработчик заходит на сайт, регистрируется (email/пароль или Google/GitHub), создаёт проект «Мой блог» — видит `projectId`, выпускает API-ключ с правом read.
2. Приглашает по email коллегу-редактора, назначает роль editor.
3. В своём приложении (Vite + React) ставит пакеты, пишет `jalyk.config.ts` с двумя-тремя типами документов, монтирует `<Studio config={...} />` на маршрут `/admin`, в настройках проекта на сайте указывает origin своего приложения.
4. Открывает `/admin`, входит своим аккаунтом Jalyk — студия показывает его проект. Создаёт документы: текст, rich-text, картинка, ссылка на другой документ, массив. Черновик → «Опубликовать».
5. На фронтенде пишет `const posts = await cms.find('post', { select: ... })` с `projectId` и ключом — получает данные с выведенными из конфига типами, только опубликованные.
6. Коллега входит в ту же студию со своего аккаунта; правки в одной вкладке мгновенно видны в другой.
7. На сайте-платформе в проекте виден график запросов к API за неделю.

Шестой пункт — наследник самой сильной части прототипа (live-обновления), седьмой — зародыш бизнес-модели.

## Состав MVP

### Сайт-платформа (`apps/web`, TanStack Start)

Минимальный, но настоящий: регистрация/вход, список проектов, создание проекта, страница проекта с тремя разделами — участники (приглашение по email со ссылкой, роли owner/editor, удаление), API-ключи (создать с правом read или read/write, показать один раз, отозвать), настройки (название, разрешённые origin'ы) — и простой график использования (запросы по дням). Не входят: оплата, тарифы, командные аккаунты-организации, восстановление пароля можно через magic link better-auth, чтобы не делать почтовый флоу дважды.

### API-сервер (`apps/api`, Effect HttpApi)

- Auth: проверка bearer-токенов (студия) и API-ключей (клиент), членство и роль в проекте — один middleware на все операции с контентом.
- Документы: CRUD, запись поля по пути (для реактивных инпутов), публикация (черновик/опубликовано — редактирование не трогает published-данные), find-запросы с фильтрами по верхнеуровневым полям и дереференсом ссылок через вложенный select.
- Снапшот схемы: студия синхронизирует сериализованную схему проекта в базу; сервер валидирует записи против неё (required, min/max, типы).
- Ассеты: presigned-загрузка в S3, таблица метаданных, список, удаление, базовые лимиты размера и типов.
- SSE-поток событий проекта с проверкой доступа.
- Учёт: счётчик запросов по проектам с агрегацией по дням.
- Инфраструктура достоверности: бэкапы Postgres (managed), Sentry, healthcheck. Для сервиса с чужим контентом это входит в MVP, а не в «потом».

### Схема контента (`@jalyk/schema`)

- `defineConfig({ documents: {...} })` — реестр, из которого выводятся все типы (решение циркулярных зависимостей).
- Типы полей: `string` (обычный/multiline/select), `number`, `boolean`, `richText` (Tiptap), `image`, `reference`, `object`, `array`. Этого хватает на блог, портфолио и каталог. Не входят: дата, геоточка, slug с автогенерацией, блоки-конструктор.
- Валидация: `required`, `min`/`max`, кастомная функция (только клиентская); декларативная часть сериализуется в снапшот для сервера.
- Заголовок, описание, иконка у документа и поля; превью документа (title из указанного поля).

### Студия (`@jalyk/studio`)

- Вход аккаунтом Jalyk (bearer-токен), экран «нет доступа к проекту».
- Список типов → список документов (превью, поиск по заголовку) → форма документа.
- Форма: реактивные инпуты с подпиской на путь и upsert с дебаунсом (перенос механики прототипа, с починкой багов инпутов из [07-feature-audit.md](docs/07-feature-audit.md)), ошибки валидации у поля, статус «черновик/опубликовано», публикация, удаление.
- Медиа: страница ассетов, загрузка с прогрессом, выбор картинки в поле.
- Live-обновления между вкладками и пользователями через SSE.
- Изоляция стилей (префикс Tailwind), тема через CSS-переменные.

### Клиент (`@jalyk/client`)

Фреймворк-независимое ядро: `createClient({ projectId, apiKey })` → `find` с типами, выведенными из конфига. React-хуки — отдельным entry point. Только чтение опубликованного; write-операции по ключу с правом write — после MVP (сценарий «наполнить контент скриптом» подождёт).

### Что осознанно НЕ входит в MVP

Оплата и тарифы (но счётчики уже есть); история версий и откат; локализация; webhooks; хуки beforeChange/afterChange; live preview сайта; ресайзы изображений; полнотекстовый поиск; миграции контента при смене схемы (пока — предупреждение в форме); кастомные роли и полевые права; co-editing (live-обновлений достаточно); CLI; шаблоны. Всё размечено по этапам в [06-long-term.md](docs/06-long-term.md).

## Порядок работ и оценки

Оценки для одного разработчика в режиме сайд-проекта (10–15 часов в неделю). По сравнению с self-hosted вариантом объём вырос: добавился сайт-платформа и серьёзный auth/изоляция, зато исчезла забота о работе в чужих окружениях.

**Этап 0. Скелет и проектирование (2 недели).** Перезаложить монорепо (`apps/web`, `apps/api`, пакеты, Vitest, examples). На бумаге: сигнатуры `defineConfig`, форма find-запроса, формат снапшота схемы, список эндпоинтов, модель данных (projects, members, api_keys, documents, assets, usage). Прошлый раз проект застрял именно на непроспектированных местах — этап пропускать нельзя.

**Этап 1. Платформенное ядро (3–4 недели).** Drizzle-схема, better-auth (email/пароль + OAuth + bearer), проекты, членство, приглашения, API-ключи, middleware изоляции и учёта. Тесты на изоляцию проектов — самые важные тесты системы: чужой проект недоступен ни сессией, ни ключом.

**Этап 2. Контентное ядро (3–4 недели).** Документы: CRUD, поле-по-пути, публикация, find с дереференсом, снапшот схемы и серверная валидация, SSE, ассеты с presigned-загрузкой. К концу этапа весь сценарий MVP проходит через HTTP без UI.

**Этап 3. Схема и типы (2–3 недели).** `defineConfig` с реестром, вывод типов find-запроса и результата (самая сложная типовая магия — дереференс в select), сериализация схемы. Мерило: автокомплит полей в examples, опечатка — ошибка компиляции.

**Этап 4. Студия (5–7 недель).** Самый большой этап: перенос наработок прототипа на новый клиент (инпуты, Tiptap, превью переиспользуются), списки, медиа, вход, изоляция стилей, SSE-инвалидация, выпиливание react-router.

**Этап 5. Сайт-платформа (3–4 недели).** TanStack Start: auth-флоу, проекты, участники, ключи, настройки origin'ов, график использования. UI делит `packages/ui` со студией.

**Этап 6. Клиент, деплой, полировка (2–3 недели).** `@jalyk/client`, деплой web+api в Docker на VPS с managed Postgres, Sentry, бэкапы, документация-quickstart, демо-видео, публикация пакетов в npm.

Итого **4.5–6.5 месяцев** в режиме сайд-проекта: при старте в конце июня 2026 ориентир MVP — конец декабря 2026 — январь 2027. Главные риски по срокам — этап 4 (UI всегда дольше) и типовая магия этапа 3; страховка та же: при затыке на типах временно упростить дереференс (ссылки отдаются как id) и вернуть в v0.2. Если захочется ускориться, сайт-платформу (этап 5) можно временно ужать до «создание проекта и ключей через CLI-скрипт», но тогда демо теряет половину убедительности — не рекомендую.

## Что переносится из текущего кода

Переживут переписывание: компоненты инпутов и механика «подписка на путь + upsert с дебаунсом», Tiptap-редактор с расширением reference, UI-кит на Base UI, концепция превью, лейаут структуры студии, сущности Project/роли как идея (с настоящей изоляцией). Умирают: всё на Prisma и tRPC, таблица Field/EAV, `apps/server`, прямой `user.upsert` с клиента, текущий OAuth-флоу с секретами в коде (секреты отозвать!).

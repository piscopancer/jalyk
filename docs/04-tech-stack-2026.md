# На чём переписывать в 2026 году

Рекомендуемый стек с учётом двух вводных. Первая — целевая архитектура: **центральная инфраструктура по модели Sanity**. Автор держит сайт управления (аккаунты, проекты, приглашения, роли, API-ключи) и API-сервер с базой; разработчикам поставляются только npm-пакеты — встраиваемая студия и клиентская библиотека запросов. Это позволяет собирать статистику использования и в перспективе брать деньги за подписки и квоты. Вторая вводная — предпочтения по инструментам: React, Effect, TanStack Router, Base UI, shadcn, Tailwind. Список почти полностью совпадает с тем, что я бы и так рекомендовал, поэтому спорить придётся мало.

## Архитектура: три приложения и три пакета

Система разделяется на части с разными жизненными циклами.

**Приложения (инфраструктура автора):**

1. **`apps/web` — сайт-платформа** (аналог sanity.io/manage). Регистрация и вход, создание проектов, приглашение участников по email, роли, выпуск и отзыв API-ключей с правами read/write, настройки проекта (разрешённые origin'ы для CORS), просмотр статистики использования; позже — тарифы и оплата. Стек: TanStack Start (стабилен с v1.0, март 2026) — здесь он на своём месте: это обычное веб-приложение с SSR, формами и дашбордами.
2. **`apps/api` — API-сервер контента.** Отдельный процесс и отдельный деплой — сознательное решение ради живучести: если сайт-платформа упал или выкатывается, студии и сайты клиентов продолжают работать, потому что ходят только в API. Всё содержательное живёт здесь: документы, find-запросы, ассеты, события, проверка сессий и API-ключей, учёт использования. Это самое нагруженное и самое ответственное приложение системы.
3. **Postgres + S3-совместимое хранилище** — управляемые сервисы или свой VPS; об этом ниже.

**Пакеты (поставляются разработчикам через npm):**

1. **`@jalyk/studio`** — React-компонент админки. Монтируется на маршруте (`/admin`) в приложении разработчика, конфигурируется `projectId` и определениями документов, ходит в центральный API. Именно так работает студия Sanity, и текущий прототип уже устроен так же.
2. **`@jalyk/client`** — клиент запросов. Принципиально **фреймворк-независимый** (ядро без React: обычные функции, возвращающие Promise, плюс подписки), чтобы использоваться где угодно — в React-приложениях, на сервере пользователя при SSR, в скриптах, в чужих фронтендах вне админки. React-хуки поверх него — отдельный entry point (`@jalyk/client/react`). Аутентификация — API-ключом проекта.
3. **`@jalyk/schema`** — `defineConfig`, `defineDocument`, `defineField`: общий слой определений, из которого выводятся типы для студии и клиента. Определения живут в коде разработчика и передаются и в студию, и в клиент — один источник правды. (API-сервер схему проекта не знает заранее — об этом важном следствии ниже.)

Из центральной модели следует ограничение, которого не было бы при self-hosted: **сервер не может полагаться на код разработчика**. Схема контента объявлена в чужом приложении, а сервер обязан валидировать запросы и данные, не имея её под рукой. Решение: студия при работе (а позже — CLI при деплое, как `sanity deploy`) синхронизирует сериализованное представление схемы (JSON: типы, поля, правила валидации) в базу, и сервер валидирует записи и find-запросы против этого снапшота. Это ещё один аргумент за декларативные правила валидации вместо произвольных функций — их можно сериализовать.

## Бэкенд (`apps/api`)

**Рантайм: Node.js LTS.** Сервер свой, совместимость с чужими окружениями не нужна, поэтому выбирается просто самое надёжное.

**Effect — да, и для центральной модели аргументы только усиливаются.** Публичный мультитенантный API — это ровно та среда, где сильные стороны Effect окупаются: HttpApi даёт декларативное описание API со схемами, из которого выводятся сервер, типизированный клиент и OpenAPI-документация; Effect Schema закрывает валидацию на границе; встроенные ретраи, таймауты, прерывание и конкурентность — это то, что для публичного сервиса иначе пишется руками; Layer-архитектура даёт DI для адаптеров (хранилище, почта, биллинг) и чистое тестирование. Минусы прежние — крутая кривая входа и меньше потенциальных контрибьюторов, — но для проекта одного автора, которому Effect нравится, перевешивают плюсы. Главное практическое следствие: **HttpApi решает задачу typed-клиента**, на которой проект застрял с tRPC, — клиент для студии и основа `@jalyk/client` выводятся из того же описания API через `HttpApiClient`, без кодогенерации.

**tRPC — убрать.** Его роль целиком закрывает Effect HttpApi, причём с настоящими HTTP-эндпоинтами (их можно дёргать не только из TypeScript) и OpenAPI бесплатно.

**База: Postgres + Drizzle ORM.** Postgres, а не SQLite: центральная база с чужим контентом требует конкурентной записи, онлайн-бэкапов, репликации и роста — это родная территория Postgres, тем более он уже в проекте. Хранение контента — документ как JSONB-строка в общей таблице `documents` с колонкой `project_id` (не отдельные таблицы и тем более не отдельные базы на проект — на старте сотни проектов спокойно живут в одной базе с индексом по `(project_id, type)` и GIN по `data`). Drizzle вместо Prisma: легче, без шага кодогенерации, SQL-близкий API упрощает работу с JSONB-операторами, и Prisma в этом репо уже показал острые углы («slomano»-upsert, `toJSON`-трюки). Изоляция проектов — в одной точке (middleware, подмешивающий `project_id` во все запросы), а не в каждом обработчике; как страховка на будущее у Postgres есть RLS.

**Auth: better-auth, два контура доступа.** Контур людей: аккаунт Jalyk (email/пароль + OAuth Google/GitHub — для центрального сервиса OAuth уместен, секреты строго в env), сессии для сайта-платформы; для студии, живущей на чужом домене, — bearer-токены (плагин better-auth) вместо кросс-доменных кук, это проще и надёжнее. Членство в проектах и роли — плагин organization или своя пара таблиц. Контур приложений: **API-ключи проекта** с правами read/write, создаваемые на сайте; хранятся хешированными, проверяются на каждый запрос, привязывают запрос к проекту — и для авторизации, и для учёта использования.

**Статистика и квоты — с первого дня, дёшево.** Middleware на API-сервере пишет факт запроса (проект, ключ, операция, объём) в таблицу-счётчик с агрегацией по дням. Этого достаточно и для дашборда «использование проекта» на сайте, и как основа будущих квот и тарифов. ClickHouse и прочая аналитическая артиллерия не нужны до десятков миллионов событий в день.

**Реалтайм: SSE.** Подписка студии (и live preview) на изменения — однонаправленный поток; SSE проще WebSocket во всём: обычный HTTP, автоматический reconnect, тривиален в Effect (Stream → Response), не требует особой настройки балансировщиков. Внутренняя механика прототипа (события по путям → точечная инвалидация ключей TanStack Query) переносится как есть; добавляется фильтрация потока по правам подписчика.

**Файлы: S3-совместимое хранилище** (Яндекс Object Storage уже выбран в прототипе — нормально для российской аудитории; абстракция-адаптер на случай смены). Загрузка — presigned URL напрямую в хранилище (не гонять файлы через API-сервер), метаданные — таблица в Postgres, привязанная к проекту (это чинит и баг удаления из [07-feature-audit.md](docs/07-feature-audit.md)). Ресайзы изображений — sharp при загрузке, отдача через CDN.

**Деплой:** Docker на VPS (или Railway/Fly для начала), `web` и `api` — отдельные контейнеры с отдельными релизами, управляемый Postgres с автоматическими бэкапами. Когда хранится чужой контент, бэкапы и мониторинг (Sentry + uptime-чекер) — не «потом», а часть MVP.

## Фронтенд

**Студия (`@jalyk/studio`): React 19, без фреймворка.** Студия остаётся встраиваемым SPA-компонентом — ей не нужен ни SSR, ни свой фреймворк. Внутренний роутинг — TanStack Router в memory-режиме с синхронизацией через splat-маршрут хозяина (текущий `BrowserRouter` из react-router конфликтует с роутером приложения-хозяина — это видно прямо в test-client, где их два). UI — Base UI 1.x + компоненты shadcn-способом в `packages/ui` + Tailwind 4 с префиксом классов для изоляции от стилей хозяина; тема — CSS-переменные. Данные — TanStack Query поверх клиента из HttpApi, ключи кешей — пути полей, как в прототипе. Редактор — Tiptap 3 (правильный выбор, остаётся). Формы как сущность не нужны — модель «поле = подписка на путь + upsert с дебаунсом» уже спроектирована и подходит лучше классических форм.

**Сайт-платформа (`apps/web`): TanStack Start + те же UI-пакеты.** Здесь фреймворк уместен: SSR для публичных страниц, server functions для работы с биллингом и приглашениями, типизированный роутинг сквозь всё приложение. Сайт и студия делят `packages/ui` — двойная отдача от одной дизайн-системы.

**Валидация в публичном API определений: декларативный DSL.** Внутри сервера — Effect Schema, но в `defineString({ validate: ... })` пользователи пишут декларативные правила (`{ required: true, min: 3 }`) с escape hatch функцией для клиентской проверки. Причина теперь жёстче, чем вкус: серверу нужна сериализуемая схема для валидации чужих записей (см. выше), а функции не сериализуются. zod как опциональный формат правил — можно добавить через Standard Schema позже.

## Монорепо и сборка

pnpm + Turborepo остаются. Сборка пакетов — tsdown (наследник tsup на Rolldown) либо tsup, публикация через changesets, тесты — Vitest (для `apps/api` — обязательны: это сервис с чужими данными; интеграционные — против реального Postgres в Docker). `apps/test-client` превращается в эталонный пример «приложение разработчика» (Vite + TanStack Router + студия + клиент) и одновременно интеграционный стенд.
